# 在真机上验证改动

## 改完必须验证，别只看代码

改代码后只读一遍就说「已完成」是不够的。本机有完整的验证闭环，用起来：

```
gradle_build  →  install_apk  →  launch_app  →  logcat_read
```

这四个是**专用工具**，比自己 `shell_execute ./gradlew` 好：它们复用构建服务的增量缓存、
解析错误、处理设备选择。优先用它们。

## 哪些改动必须装机才能确认

| 改动 | 为什么不能只看代码 |
|---|---|
| UI 布局、主题、颜色 | 颜色由主题 attr 解析，可能落到框架兜底值；布局在不同形态下会退化 |
| 权限、Manifest 声明 | 运行时才生效，声明写错不会编译报错 |
| 签名、applicationId | 只在打包阶段暴露 |
| native 库 | `.so` 是否被打进 APK、ABI 是否齐全，要解包才看得到 |
| 生命周期、异步时序 | 竞态与顺序问题只有真跑才出现 |

## 读日志的正确姿势

失败时先读**完整错误**再改代码。常见的归因错误：

- 报错指向 A，真正原因在 B（例如链接报 `undefined symbol`，原因在 `CMakeLists.txt` 漏了源文件）
- 报错是上游工具转述的，原始错误在更早几行
- 只看到最后一行 `BUILD FAILED` 就开始猜

用 `logcat_read` 时要**过滤**（按 tag 或关键字），否则会被系统日志淹没。
应用崩溃时先搜 `FATAL EXCEPTION` 与自己的包名。

## 编译通过 ≠ 功能正确

构建成功只说明语法与类型正确。功能要这样验：

1. 装上设备
2. 启动应用
3. 触发你改的那条路径
4. 读日志确认没有异常
5. 必要时截图看 UI

**别把「构建成功」当成「任务完成」**——除非用户要的就是让它编译过。

## 失败要如实报告

改不动、修不好、验证失败时，直接说清楚：改了什么、现象是什么、你判断的原因是什么、
还需要什么。不要为了显得完成了而省略失败，也不要声称验证过而实际没跑。
